# Как участвовать в разработке

## Стратегия ветвления

Мы используем **GitHub Flow**.

**Почему именно он**: у нас небольшая команда из трёх человек и одна версия системы: параллельно поддерживать несколько релизов не нужно. Нет отдельных окружений с долгоживущими ветками, а изменения мы хотим интегрировать часто, чтобы конфликты оставались маленькими.

- `main` всегда рабочая и защищена: прямая запись отклоняется
- Ветка под задачу создаётся от `main` и живёт не дольше недели
- Слияние только через запрос на слияние с зелёным конвейером и одобрением ревьюера
- Запросы сливаются способом squash, ветка после слияния удаляется

### Именование веток

Формат: `<тип>/<краткое-описание-через-дефис>`

| Тип | Когда |
| --- | --- |
| `feat/` | Новая возможность |
| `fix/` | Исправление |
| `refactor/` | Изменение без смены поведения |
| `docs/` | Документация |
| `chore/` | Рутина, конфигурация |

Примеры: `feat/booking-cancel`, `docs/contributing`, `chore/repo-setup`.

## Формат коммитов

Формат: `<тип>(<область>): <краткое описание>`

Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`.

Область необязательна, но полезна. Для нашего проекта подходят области по ограниченным контекстам: `catalog` (точки и залы), `booking` (слоты и брони), `payments` (тарифы и оплата), `notifications` (уведомления).

Проверка: по сообщению понятно, что изменилось, без открытия разницы. Сообщения вроде «фикс», «работа» или «.» не принимаются.

## Требования к запросу на слияние

Заголовок оформляется по формату коммита. В описании обязательно:

- **Что изменено**: смысл, а не пересказ разницы
- **Почему**: задача или причина
- **Как проверить**: шаги для ревьюера

Размер: ориентир до 400 строк изменений. Если больше, режьте по сценариям, чтобы после каждого запроса система оставалась рабочей.

Перед открытием запроса убедитесь, что конвейер зелёный, а ветка актуальна относительно `main`.

## Что проверяется при ревью

В этом порядке:

1. Замысел: решает ли изменение заявленную задачу
2. Корректность: логика, граничные случаи, отказы
3. Тесты: упадёт ли тест, если сломать код
4. Безопасность: валидация, секреты, права
5. Читаемость: будет ли понятно через полгода
6. Стиль: проверяется машиной, не человеком

Для нашего проекта особое внимание уделяем бронированию: при ревью проверяем, что две одновременные попытки занять один слот не приводят к двойной брони.

### Формат комментариев

Помечайте тип замечания: `praise:`, `question:`, `suggestion:`, `issue:`, `nit:`.

Замечание относится к коду, а не к автору. Хороший комментарий: что не так → к чему приведёт → вариант решения.

### Время ответа

Ревью даётся в течение суток. Если дольше, ветка расходится с основной, и растёт риск конфликтов.

## Определение завершённости

Задача считается сделанной, если:

- [ ] Код влит в основную ветку через запрос на слияние
- [ ] Запрос прошёл ревью второго участника с содержательными комментариями
- [ ] Конвейер проверок зелёный
- [ ] Написаны тесты на критерии приёмки, они проходят
- [ ] Документация обновлена: README или соответствующий файл в `docs/`
- [ ] Добавлена запись в `docs/CHANGELOG.md`
- [ ] Изменение проверено на чистом окружении (не только «у меня работает»)
- [ ] Для брони и оплаты: проверен случай конфликта (две попытки занять один слот)

Подробнее о процессе команды: [docs/process.md](docs/process.md).
